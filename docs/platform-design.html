UI 测试平台 · 技术架构方案

基于 AI Agent 的 UI 自动化测试平台

以 AI Agent 为核心执行单元的测试平台：用例以自然语言描述，由多个测试 Agent 并行执行，每一步都留痕，报告实时可看、失败可归因。LLM 调用 DeepSeek 官方 API（低定价、免 GPU 运维），其余组件全部开源、本地部署，不依赖任何其他付费服务。方案面向 2026 年的框架生态：Playwright 已内置面向 Agent 的接口（v1.60 的 boxes），MCP 已成为 Agent 接入工具的标准协议。

结论先行

  1. 01
    执行内核双轨。回归用例跑确定性 Playwright / Appium 脚本；探索性用例、自愈、异常处理交给 LLM Agent。2026 年行业共识：Agentic 是对确定性自动化的补充，而非替代。
  2. 02
    工具层 MCP 标准化。浏览器、移动端、断言能力封装为 MCP Server，LLM 可替换而工具契约稳定。
  3. 03
    多 Agent = Master-Worker + 任务队列。Master 拆解测试计划，Worker 容器化、无状态、按浏览器实例水平扩容。
  4. 04
    报告 = 步骤级事件流。每一步（工具调用、LLM 决策、断言结果、截图）作为事件实时上报，报告中心聚合为时间轴报告并做 AI 失败归因。
  5. 05
    起步选型。Playwright ≥ 1.60 + Appium 2.0 + Python/FastAPI + Redis 队列 + PostgreSQL/MinIO；Agent 循环用自研轻量循环（OpenAI 兼容协议）；LLM 调用 DeepSeek 官方 API——deepseek-chat 做日常动作决策、deepseek-reasoner 做拆解 / 归因等复杂推理，接口可随时降级为本地开源权重。
01

设计目标与原则

行业现状：约 80% 的 UI 用例生命周期被 locator 修复、超时与环境问题占据；Appium 类方案 flakiness 普遍在 15% 以上。平台的核心命题是把 AI 能力用在维护成本最高的环节。

目标

  • 多 Agent 并行执行——用例级任务分发，Agent 池水平扩容，账号 / 设备等共享资源受控编排。
  • 报告生成与查看——步骤级 trace、截图 / 视频、LLM 决策轨迹；执行中实时聚合，事后趋势与基线对比。
  • 降低维护成本——locator 失效自愈、自然语言生成用例、失败模式知识库复用。
  • 可信执行——断言由确定性代码校验（LLM 只负责路径选择，不负责下结论）；全程留痕，失败可归因。
  • 成本可控——LLM 走 DeepSeek 官方 API（低定价、无 GPU 运维）；其余组件全部开源、可自托管。

原则

  • 混合执行：确定性脚本（快、稳、便宜）与 Agentic 执行（自适应、可探索）按用例模式路由。
  • MCP 标准化：所有自动化能力通过 MCP 暴露，Agent 与框架解耦。
  • 无状态 Agent：执行状态在队列与数据库中，Worker 可随时重建，扩容与故障恢复简单。
  • 留痕优先：每个决策与动作都是可检索的事件——报告、审计、失败知识库共用同一条事件流。
  • 本地优先：除 LLM 外全部组件开源、可自托管（Apache-2.0 / MIT / BSD）；模型接口走 OpenAI 兼容协议，DeepSeek API 与本地开源权重（Qwen3 等）可互换降级。
02

总体架构

五层结构。控制流自上而下（提交 → 编排 → 分发 → 执行），事件流自 Agent 直通数据层——报告系统挂在事件流上，而不是事后扫描结果表。

两层控制语义

控制流

接入层提交测试计划 → Master Agent 拆解为用例任务并入队 → 调度器按资源可用性分发 → Worker 执行。控制流是低频的、可重试的。

事件流

Worker 的每一步动作（工具调用、LLM 决策、断言结果、截图、视频片段）都是高频事件，直接写入消息总线。报告中心订阅总线实时聚合；同一份事件流回放即可重建任意历史报告，也可喂给失败知识库。

03

多 Agent 执行机制

Master-Worker 模型：一个 Master Agent 负责拆解与调度，N 个 Worker Agent 负责执行。两者职责分离，Worker 保持无状态。

Master 与 Worker

角色职责技术形态
Master Agent测试计划 → 用例任务拆解；按依赖关系排序；申请账号 / 设备资源；汇总各任务结果生成计划级结论LLM Agent + 调度 API 工具（低频调用）
Worker Agent领取单个用例任务，驱动浏览器 / 设备执行；产出步骤事件流；失败时自愈重试容器内 LLM Agent + MCP Client + Playwright / Appium 运行时
调度器任务队列、优先级、重试、资源锁；Worker 心跳与回收确定性代码，不含 LLM
决策

调度器必须是确定性代码。LLM 只出现在 Master（拆解）和 Worker（执行路径选择）两处——队列、重试、资源锁这些环节引入 LLM 只会增加不确定性，没有收益。

任务状态机

queued→ assigned→ running→ passed failed→ retrying→ quarantined

每个用例是一个可重试的任务。失败后自动重试（携带上一次的 Agent 上下文与失败事件），连续失败超过阈值进入 quarantined 隔离区，不再占用常规资源，由人工或知识库修复后重新入队。

并发与容错

  • 扩容单元 = 浏览器实例。一个 Worker 容器跑一个浏览器会话，K8s HPA 按队列深度伸缩——与 Agent 数量解耦，资源模型简单。
  • 共享资源锁。账号、测试数据、设备等互斥资源用 Redis 分布式锁排队，避免两个 Agent 抢同一账号。
  • 心跳回收。调度器 watchdog 检测 Worker 心跳超时即回收任务重新入队；任务结果幂等上报（按 task_id + attempt 去重）。
  • 执行上限。每个任务有步骤数、时长与推理 token 三重上限（平台侧强制），防止 Agent 失控烧算力。
04

测试 Agent 执行引擎

Worker 内部是一个「观察 → 决策 → 行动 → 校验」循环。关键选型：用 Playwright 1.60 的 boxes（带坐标的 ARIA 快照）替代逐屏截图做视觉推理——文本化、便宜、快一个数量级；截图只用于报告留痕与视觉断言。

工具集（MCP 封装）

工具能力实现
browser_*导航、点击、输入、等待、截图、读取 ARIA 快照Playwright MCP Server（官方，MIT）
mobile_*移动端同类能力Appium 2.0 自封装 MCP Server（Apache-2.0）
assert_*文本 / 元素 / 属性断言，返回结构化结果确定性代码，非 LLM 判断
visual_diff截图与基线比对，输出差异区域pixelmatch（MIT）/ 自研，失败时把差异图交给视觉模型判断是否为预期变化
data_*造数、API 请求、数据库校验平台服务侧工具

两种执行模式

  • 探索模式（agentic）：自然语言用例直接交给 Agent 执行，路径由 LLM 现场决策。适合新用例验证、偶发路径、异常场景。
  • 固化模式（deterministic）：Agent 探索通过的路径固化为 Playwright spec / pytest 脚本，后续回归走确定性执行——快、稳、便宜。探索一次，固化长期。

模型路由、自愈与上下文优化

  • 模型服务：LLM 调用 DeepSeek 官方 API（OpenAI 兼容协议）。deepseek-chat 负责高频动作决策（JSON 输出模式，快且便宜）；deepseek-reasoner 负责低频复杂推理——计划拆解、失败归因、自愈重定位。接口层抽象后，可随时降级为本地开源权重（Qwen3 经 Ollama / vLLM，协议不变）。
  • 自愈：locator 失效 → LLM 依据快照重新定位 → 新定位写入元素库（与应用版本绑定）→ 回归直接复用。元素库标注来源（人工 / 自愈），自愈定位需通过一次回归验证后才转正。
  • 上下文优化：DOM 快照只保留可交互元素与必要文本，历史步骤滚动裁剪，防止长用例上下文膨胀；每步 token 用量入账，报告中心呈现算力成本。
决策

Agent 循环采用自研轻量循环（基于 OpenAI 兼容协议 + JSON 动作协议），每轮的 hooks 就是事件留痕点，报告与审计从这里长出；browser-use（MIT）与 LangGraph 作为演进备选。工具层 v1 实现为内部工具注册表（与 MCP 工具契约对齐），后续可平滑切换到官方 Playwright MCP Server。

05

报告中心

报告不是执行后的产物，而是事件流的投影：执行中即可看，执行完可回放。

事件流

事件内容报告呈现
step_started步骤目标、序号、Agent 上下文摘要时间轴节点
llm_decisionLLM 选择该动作的理由摘要「为什么点这里」展开面板
tool_call工具名、参数、耗时、结果摘要时间轴内联卡片
screenshot截图 + DOM / ARIA 快照，MinIO 工件引用步骤缩略图，点击放大
assertion断言表达式与实际值通过 / 失败标记
video_segmentPlaywright screencast 视频段整段回放
step_failed异常、失败瞬间快照、重试决策红色高亮 + 失败分析链接

报告形态

  • 实时 Web 报告：用例时间轴 + 截图 / 快照 / 视频 + LLM 决策轨迹 + 断言结果，执行中逐步点亮。
  • AI 失败归因：执行结束后由分析 Agent 把失败归类为五类——产品缺陷 / 环境问题 / 用例设计问题 / locator 漂移 / Agent 误判，并自动生成缺陷草稿（含复现步骤与证据引用），确认后一键推缺陷系统。归因结果写入失败知识库，同类失败再次出现时直接引用历史结论。
  • Allure 兼容导出：把事件流转换为 Allure 格式导出（Apache-2.0），兼容团队既有报告流程与 CI 集成；如已有 ReportPortal 基建（Apache-2.0，自托管），也可作为聚合后端。
  • 趋势面板：通过率、flakiness（用例级重跑率）、执行时长、推理成本（GPU 时 / token 量）四个核心指标；版本间基线对比（新版本 vs 基线截图 / 通过率回归标记）。
决策

首选自研 Web 报告（实时性 + AI 归因是差异化能力），Allure 只做导出兼容而非主报告——避免被第三方报告格式束缚事件模型的表达能力。

06

技术栈选型

2026 年的选型基线：Web 选 Playwright（官方 MCP Server、v1.60 boxes 面向 Agent 设计），移动选 Appium 2.0（仍是原生移动 E2E 的开放标准，暂无 AI 原生替代）。全表组件均为开源，协议标注于选型后。

层次推荐（协议）理由备选
Web 内核Playwright ≥ 1.60（Apache-2.0）+ 官方 Playwright MCP（MIT）boxes（带坐标 ARIA 快照）为 Agent 设计；screencast 视频；trace 原生；跨 Chromium/Firefox/WebKitSelenium 4 + BiDi（存量团队）
移动内核Appium 2.0（Apache-2.0，UiAutomator2 / XCUITest）双平台统一 API；生态最全；自封装 MCP Server 成本低Maestro（轻量冒烟）
Agent 循环自研轻量循环 + JSON 动作协议 + Playwright自持循环的每轮 hooks 即事件留痕点；OpenAI 兼容协议，模型可插拔；无闭源依赖browser-use（MIT，快速原型 / 参考实现）、LangGraph（MIT）
模型服务DeepSeek 官方 API（deepseek-chat / deepseek-reasoner）低定价、免 GPU 运维；JSON 输出模式适合动作协议；OpenAI 兼容接口，可随时降级本地开源权重本地 Qwen3 + Ollama / vLLM（协议不变）
后端Python 3.12 + FastAPI（MIT）AI 生态最全；与 pytest-playwright 固化产物同栈；async 原生Node.js / TypeScript
任务编排Redis + Arq（MIT）起步，规模化后迁 Temporal（MIT，自托管）P0 轻量即可跑；复杂重试 / 工作流 / 补偿用 Temporal 语义更完整Celery（BSD）
前端静态 SPA 控制台（零依赖零构建，开箱即用）无需 Node 环境即可运行；由后端直接托管；时间轴 / 表格视图自研实现React + Ant Design（MIT，规模化后重构路径）
存储PostgreSQL 16（PostgreSQL 协议，+ pgvector）+ Redis + MinIO（AGPL-3.0）元数据 + 向量检索（失败知识库）+ 对象存储一体；自托管可控MySQL、SeaweedFS
报告自研 Web 报告 + Allure（Apache-2.0）导出实时 + AI 归因是核心能力，不被第三方格式束缚ReportPortal（Apache-2.0，自托管）
可观测OpenTelemetry（Apache-2.0）+ Prometheus / Grafana（自托管）LLM 调用链路与算力消耗可见是 AI 平台的刚需自研埋点
部署Docker + K8s（Apache-2.0）Worker 池 HPA、会话隔离、镜像化浏览器Docker Compose（P0 阶段）
本地优先的边界

除 LLM 外所有组件开源、可自托管、无许可费。LLM 按既定决策调用 DeepSeek 官方 API（低定价、免 GPU 运维）；所有模型接口保持 OpenAI 兼容——若需数据合规或离线运行，在网关处替换为本地开源权重（Qwen3 + Ollama / vLLM）即可，平台代码零改造。

取舍说明

本方案自托管执行（Worker 跑在自有容器里驱动本地浏览器），而非依赖托管浏览器云（Browserbase 等）或托管 Agent 平台——测试目标通常是内网环境，出网托管不适用；同时也与「开源优先」一致。若目标站是公网且团队小，托管方案可作为 P0 的降本捷径，接口层保持一致即可迁移。

数据模型

核心实体八个，全部以 PostgreSQL 为主存储；事件与工件走 MinIO。

实体关键字段说明
test_casemode（agentic / deterministic）、steps（JSON）、版本号用例可被 LLM 生成、可固化；版本化以支持基线对比
test_plan用例集、依赖关系、调度策略、触发方式Master 的输入；支持 CI 触发与定时
test_runplan 引用、被测环境与版本、起止时间、汇总状态一次完整执行
test_taskrun / case 引用、状态机状态、重试次数、agent 标识队列中的任务单元，幂等键 task_id + attempt
agent_sessiontask 引用、worker 标识、浏览器会话、推理用量（token / 耗时）算力统计与审计来源

风险与对策

风险影响对策
LLM API 依赖网络波动 / 服务不可用 / 密钥泄露风险接口抽象 + 指数退避重试；密钥只存服务端环境变量；协议 OpenAI 兼容，可降级本地开源权重兜底
API 成本LLM 调用量随用例数线性增长DeepSeek 低定价；deepseek-chat / reasoner 分级路由；DOM 快照裁剪 + token 上限；固化模式把高频用例移出 LLM
LLM 不确定性误判通过 / 失败，路径漂移断言由确定性代码执行；关键回归固化；探索模式的结论标注「AI 执行」并支持人工确认
安全与合规Agent 接触敏感页面数据与账号，页面内容经 API 外发Worker 容器隔离 + 网络白名单；敏感数据在模型请求侧脱敏；合规要求高时切换本地开源权重；全量审计事件
稳定性Agent 卡死、Worker 崩溃、结果丢失watchdog 心跳回收、幂等上报、任务级重试、quarantine 隔离、步骤数 / 时长上限
效果预期落差「AI 测试」宣传与实际能力差距P0 先拿 10 条真实用例验证成功率与成本，达标再扩——效果数据先于平台投入

UI Testing Platform · Technical Architecture Proposal

AI-Agent-Based UI Test Automation Platform

A testing platform with AI agents as its core execution unit: cases are described in natural language, executed in parallel by multiple test agents, with every step logged, reports viewable in real time, and failures attributable. The LLM calls the official DeepSeek API (low pricing, no GPU ops); everything else is open-source and self-hosted, with no other paid services involved. The design targets the 2026 framework ecosystem: Playwright ships agent-facing interfaces (boxes in v1.60), and MCP has become the standard protocol for agents to access tools.

TL;DR

  1. 01
    Dual-track execution kernel. Regression cases run deterministic Playwright / Appium scripts; exploratory cases, self-healing and exception handling go to the LLM agent. The 2026 industry consensus: agentic complements deterministic automation — it does not replace it.
  2. 02
    Tool layer standardized via MCP. Browser, mobile and assertion capabilities are wrapped as MCP servers — the LLM is swappable while the tool contract stays stable.
  3. 03
    Multi-agent = Master-Worker + task queue. The Master decomposes test plans; workers are containerized, stateless, and scale horizontally by browser instance.
  4. 04
    Reports = a step-level event stream. Every step (tool call, LLM decision, assertion result, screenshot) is reported in real time as an event; the report center aggregates events into a timeline report and performs AI failure attribution.
  5. 05
    Starting stack. Playwright ≥ 1.60 + Appium 2.0 + Python/FastAPI + Redis queue + PostgreSQL/MinIO; a lightweight in-house agent loop (OpenAI-compatible protocol); LLM via the DeepSeek official API — deepseek-chat for day-to-day action decisions, deepseek-reasoner for complex reasoning like decomposition / attribution, with the interface downgradable to local open weights at any time.
01

Goals & Principles

Industry reality: roughly 80% of a UI case's lifecycle is consumed by locator fixes, timeouts and environment issues; Appium-style solutions commonly see flakiness above 15%. The platform's core proposition is applying AI where maintenance costs are highest.

Goals

  • Multi-agent parallel execution — case-level task distribution, horizontal scaling of the agent pool, controlled orchestration of shared resources (accounts / devices).
  • Report generation & viewing — step-level traces, screenshots / videos, LLM decision trails; real-time aggregation during execution, post-hoc trends and baseline comparison.
  • Lower maintenance cost — locator self-healing, natural-language case generation, reusable failure-pattern knowledge base.
  • Trustworthy execution — assertions verified by deterministic code (the LLM picks paths, never verdicts); full traceability, failures attributable.
  • Controlled cost — LLM via the DeepSeek official API (low pricing, no GPU ops); everything else open-source and self-hostable.

Principles

  • Hybrid execution: deterministic scripts (fast, stable, cheap) and agentic execution (adaptive, exploratory) routed by case mode.
  • MCP standardization: all automation capabilities exposed via MCP, decoupling agents from frameworks.
  • Stateless agents: execution state lives in the queue and database; workers can be rebuilt at any time — scaling and recovery stay simple.
  • Trace-first: every decision and action is a searchable event — reports, audits and the failure knowledge base share one event stream.
  • Local-first: everything except the LLM is open-source and self-hostable (Apache-2.0 / MIT / BSD); the model interface follows the OpenAI-compatible protocol, so the DeepSeek API and local open weights (Qwen3 etc.) are interchangeable fallbacks.
02

Overall Architecture

Five layers. The control flow goes top-down (submit → orchestrate → dispatch → execute); the event stream runs from agents straight to the data layer — the report system subscribes to the event stream instead of scanning result tables afterwards.

Two control semantics

CONTROL FLOW

The access layer submits a test plan → the Master Agent splits it into case tasks and enqueues them → the scheduler dispatches by resource availability → workers execute. The control flow is low-frequency and retryable.

EVENT FLOW

Every worker action (tool call, LLM decision, assertion result, screenshot, video segment) is a high-frequency event written directly to the message bus. The report center subscribes and aggregates in real time; replaying the same event stream rebuilds any historical report — the same stream also feeds the failure knowledge base.

03

Multi-Agent Execution

A Master-Worker model: one Master Agent decomposes and schedules, N Worker Agents execute. Duties are separated; workers stay stateless.

Master vs Worker

RoleResponsibilitiesForm
Master AgentTest plan → case task decomposition; ordering by dependencies; requesting account / device resources; aggregating task results into a plan-level verdictLLM agent + scheduling API tools (low-frequency calls)
Worker AgentClaims a single case task, drives the browser / device; produces the step event stream; self-heals and retries on failureContainerized LLM agent + MCP client + Playwright / Appium runtime
SchedulerTask queue, priorities, retries, resource locks; worker heartbeats and reclamationDeterministic code, no LLM
DECISION

The scheduler must be deterministic code. The LLM appears in exactly two places — the Master (decomposition) and the Worker (execution path selection). Introducing an LLM into queueing, retries or resource locks adds uncertainty with no payoff.

Task state machine

queued→ assigned→ running→ passed failed→ retrying→ quarantined

Each case is a retryable task. On failure it retries automatically (carrying the previous agent context and failure events); consecutive failures past the threshold move it to quarantined, out of regular resources, re-enqueued after manual or knowledge-base repair.

Concurrency & fault tolerance

  • Scaling unit = browser instance. One worker container runs one browser session; K8s HPA scales by queue depth — decoupled from agent count, a simple resource model.
  • Shared resource locks. Mutually exclusive resources (accounts, test data, devices) queue behind Redis distributed locks, so two agents never grab the same account.
  • Heartbeat reclamation. The scheduler's watchdog reclaims and re-enqueues tasks when a worker heartbeat times out; results are reported idempotently (dedup by task_id + attempt).
  • Execution caps. Every task has triple caps — step count, duration and reasoning tokens (platform-enforced) — to keep an agent from burning compute.
04

Agent Execution Engine

Inside a worker runs an observe → decide → act → verify loop. Key choice: use Playwright 1.60's boxes (ARIA snapshots with coordinates) instead of per-screen screenshots for visual reasoning — textual, cheap, an order of magnitude faster; screenshots are kept only for report evidence and visual assertions.

Toolset (MCP-wrapped)

ToolCapabilityImplementation
browser_*Navigate, click, type, wait, screenshot, read ARIA snapshotOfficial Playwright MCP Server (MIT)
mobile_*Same capabilities for mobileAppium 2.0 custom MCP server (Apache-2.0)
assert_*Text / element / attribute assertions returning structured resultsDeterministic code, not LLM judgment
visual_diffScreenshot vs baseline comparison, outputting diff regionspixelmatch (MIT) / in-house; on failure the diff image goes to a vision model to judge whether the change is expected
data_*Data seeding, API requests, database verificationPlatform-side service tools

Two execution modes

  • Explore mode (agentic): natural-language cases go straight to the agent; paths are decided live by the LLM. For new-case validation, occasional paths, exceptional scenarios.
  • Cure mode (deterministic): agent-explored passing paths are cured into Playwright specs / pytest scripts; subsequent regression runs go deterministic — fast, stable, cheap. Explore once, cure for good.

Model routing, self-healing & context optimization

  • Model service: the LLM calls the DeepSeek official API (OpenAI-compatible protocol). deepseek-chat handles high-frequency action decisions (JSON output mode, fast and cheap); deepseek-reasoner handles low-frequency complex reasoning — plan decomposition, failure attribution, self-heal re-location. The interface layer allows an anytime downgrade to local open weights (Qwen3 via Ollama / vLLM, protocol unchanged).
  • Self-healing: a locator breaks → the LLM re-locates from the snapshot → the new locator is written to the element repo (bound to the app version) → regression reuses it directly. The repo records the source (manual / healed); healed locators are promoted only after passing one regression verification.
  • Context optimization: DOM snapshots keep only interactive elements and essential text; history steps are windowed to prevent context bloat in long cases; per-step token usage is accounted and surfaced as compute cost in the report center.
DECISION

The agent loop is a lightweight in-house loop (OpenAI-compatible protocol + JSON action protocol); each round's hooks are the event trace points from which reporting and auditing grow. browser-use (MIT) and LangGraph remain evolution options. The tool layer ships as an internal tool registry aligned with the MCP tool contract, so switching to the official Playwright MCP Server later is a smooth migration.

05

Report Center

Reports are not a post-execution artifact — they are a projection of the event stream: viewable during execution, replayable after.

Event stream

EventContentRendered as
step_startedStep goal, sequence number, agent context summaryTimeline node
llm_decisionWhy the LLM chose this action (summary)"Why this click" expandable panel
tool_callTool name, args, duration, result summaryInline timeline card
screenshotScreenshot + DOM / ARIA snapshot, MinIO artifact referenceStep thumbnail, click to enlarge
assertionAssertion expression and actual valuePass / fail badge
video_segmentPlaywright screencast video segmentFull segment replay
step_failedException, snapshot at failure, retry decisionRed highlight + failure analysis link

Report formats

  • Real-time web report: case timeline + screenshots / snapshots / video + LLM decision trail + assertion results, lighting up step by step during execution.
  • AI failure attribution: after execution, an analysis agent classifies failures into five categories — product bug / environment issue / case design issue / locator drift / agent misjudgment — and drafts a defect automatically (repro steps + evidence references); one click pushes it to the defect system. Attribution results enter the failure knowledge base; recurring failures reference historical conclusions directly.
  • Allure-compatible export: the event stream converts to Allure format (Apache-2.0), compatible with existing team report flows and CI integration; existing ReportPortal infrastructure (Apache-2.0, self-hosted) can also serve as the aggregation backend.
  • Trend dashboard: four core metrics — pass rate, flakiness (case-level rerun rate), execution duration, inference cost (GPU time / tokens); cross-version baseline comparison (new version vs baseline screenshots / pass-rate regression flags).
DECISION

Prefer the in-house web report (real-time + AI attribution are the differentiators); Allure is export compatibility only, not the primary report — avoid letting a third-party report format constrain the event model's expressiveness.

THE BOUNDARY OF LOCAL-FIRST

Everything except the LLM is open-source, self-hostable and license-free. The LLM calls the DeepSeek official API per the established decision (low pricing, no GPU ops); all model interfaces stay OpenAI-compatible — for data compliance or offline operation, swap in local open weights at the gateway (Qwen3 + Ollama / vLLM) with zero platform code changes.

TRADE-OFFS

This design self-hosts execution (workers run in our own containers driving local browsers) rather than relying on a hosted browser cloud (Browserbase etc.) or hosted agent platforms — test targets are usually intranet environments where egress hosting doesn't apply; it also aligns with open-source-first. If the target site is public and the team is small, a hosted option can be a P0 cost shortcut; keep the interface layer consistent and migration stays open.

08

Implementation Roadmap

Three phases; each closes with a usable loop rather than building the full architecture at once.

P0 · Single Agent Works

Validate the core hypothesis

  • DeepSeek API + Playwright + lightweight loop
  • 10 real cases, explore-mode execution
  • JSON report + screenshot evidence
  • Verify: can the agent reliably complete multi-step cases? What's the per-case reasoning cost?
2–3 weeks
P1 · Platformization

Multi-agent + report center

  • Case management (NL authoring + versioning)
  • Redis queue + Master-Worker, K8s worker pool
  • deepseek-chat / reasoner tiered routing
  • Event-stream bus + real-time web report
  • Element repo + failure retry and quarantine
4–6 weeks
P2 · Intelligence

Self-healing & accumulation

  • Locator self-heal loop (probe → update → verify & promote)
  • Cure mode: explore paths generate Playwright specs
  • AI failure attribution + defect drafts + failure knowledge base
  • Visual regression, mobile agent, Allure export, CI integration
Continuous iteration
